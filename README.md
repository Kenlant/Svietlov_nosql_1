# Svietlov_nosql_1

Навчальний проєкт з MongoDB: датасет Spotify Tracks Dataset (близько 114 тисяч треків) завантажується в MongoDB Atlas у колекцію `spotify.tracks_raw` (плоска структура CSV), далі агрегацією MQL перетворюється на колекцію `spotify.tracks` (вкладені аудіохарактеристики, масив виконавців, обчислювані поля), після чого над нею виконуються запити частини 2.

## Структура репозиторію

Скрипти: `scripts/01_load_data.py` (CSV -> `tracks_raw`), `scripts/02_transform.js` (`tracks_raw` -> `tracks`, MQL), `queries/part2_queries.js` (запити частини 2); також `.env.example` і `requirements.txt`. Завантажувач - пакет `spotify/`, розділений на `domain`, `application` та `infrastructure`; `scripts/01_load_data.py` збирає їх разом.

## Налаштування оточення

1. Зареєструйтеся на mongodb.com/atlas і створіть кластер (AWS, найближчий регіон). Atlas M0 уже є replica set із трьох нод, окремо налаштовувати нічого не потрібно.
2. У Database Access створіть користувача з паролем.
3. У Network Access додайте свій IP (або 0.0.0.0/0 для розробки).
4. Connect -> Drivers: скопіюйте рядок `mongodb+srv://...`.
5. Залежності Python:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

6. Встановіть `mongosh` окремо. Без локального встановлення можна запускати через `npx -y mongosh@2.3.8` (остання версія з npm у момент перевірки падала з помилкою `Cannot find module 'mongodb-redact'`, тому версію зафіксовано).
7. Створіть `.env` із шаблону й заповніть його:

```bash
cp .env.example .env
```

```text
MONGO_URI='mongodb+srv://<db_username>:<db_password>@cluster1.wcg2gkr.mongodb.net/'
```

Значення `MONGO_URI` беріть в одинарні лапки: в URI трапляється `&`, а пароль може містити `$`, і без лапок `source .env` ламається.

8. Датасет. Файл `dataset.csv` ([Spotify Tracks Dataset](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset) з Kaggle) уже лежить у корені репозиторію. `.env` внесено в `.gitignore`.

Порядок запуску (з кореня репозиторію):

```bash
python3 scripts/01_load_data.py
set -a; source .env; set +a
mongosh "$MONGO_URI" --file scripts/02_transform.js
mongosh "$MONGO_URI" --file queries/part2_queries.js
```

`mongosh` не читає `.env`, тому URI передається з оточення, а не вшивається в скрипти. Замість `mongosh` можна використати `npx -y mongosh@2.3.8`.

Результат завантаження: прочитано 114000 рядків, у `tracks_raw` вставлено 113999 (рядки без `artists` або `track_name` відкидаються). Результат трансформації: 113999 документів у `tracks`; за `popularity_tier`: low 65412, medium 43115, high 5472; 30075 треків мають більше одного виконавця.

## Схема даних

Колекція `tracks` створюється скриптом `scripts/02_transform.js` з плоскої `tracks_raw`. Реальний документ (`findOne()`):

```json
{
  _id: ObjectId('6afdbd5b87fa1b836c19a96d'),
  track_id: '5SuOikwiRyPMVoIQDJUgSV',
  album_name: 'Comedy',
  track_name: 'Comedy',
  popularity: 73,
  duration_ms: 230666,
  explicit: false,
  track_genre: 'acoustic',
  artists: [
    'Gen Hoshino'
  ],
  audio_features: {
    danceability: 0.676,
    energy: 0.461,
    loudness: -6.746,
    speechiness: 0.143,
    acousticness: 0.0322,
    instrumentalness: 0.00000101,
    liveness: 0.358,
    valence: 0.715,
    tempo: 87.917,
    key: 1,
    mode: 0,
    time_signature: 4
  },
  duration_sec: 230.7,
  popularity_tier: 'high'
}
```

Вкладені та обчислювані поля:
- `artists` - масив рядків: рядок CSV розбито за `;`, імена обрізано від пробілів (`$split` + `$map` + `$trim`);
- `audio_features` - вкладений об'єкт із 12 аудіохарактеристиками (`danceability`, `energy`, `loudness`, `speechiness`, `acousticness`, `instrumentalness`, `liveness`, `valence`, `tempo`, `key`, `mode`, `time_signature`);
- `duration_sec` - `duration_ms / 1000`, округлено до 1 знака;
- `popularity_tier` - `high` при popularity >= 70, `medium` при 40-69, `low` при < 40;
- решта полів скопійовано з `tracks_raw` (`explicit` завантажувач приводить до bool).

## Частина 1 - відповіді на теоретичні питання

### Чому аудіо-характеристики винесені в окремий об'єкт audio_features, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?

У CSV дванадцять числових полів (`danceability`, `energy`, `loudness`, ..., `time_signature`) стоять поруч із описовими (`track_name`, `album_name`, `track_genre`). Це два різні за природою набори: метадані описують, що це за трек, а аудіо-характеристики є результатом аналізу звуку. Об'єкт `audio_features` розділяє їх, і документ читається як сутність із чітким блоком метрик, а не як рівне "простирадло" з 20+ полів.

Практичні вигоди: усю групу можна взяти однією проєкцією (`audio_features: 1`) або, навпаки, відкинути (`audio_features: 0`), коли потрібні лише метадані; у запитах видно, що поле належить саме аудіоаналізу (`audio_features.danceability`, `audio_features.tempo`, як у Завданнях 1, 3 і 4); схему легко розширити новою метрикою, не засмічуючи верхній рівень.

Вкладення вигідне, коли поля завжди читаються й змінюються разом, належать документу у відношенні 1:1, мають обмежений розмір і не мають власного життєвого циклу. Усе це правда для аудіохарактеристик треку: вони обчислені один раз і не ростуть.

Проблеми: шляхи довші в кожному запиті, проєкції та індексі (`audio_features.tempo`); складені індекси по кількох вкладених полях громіздкі; у `$group`/`$project` глибоке вкладення ускладнює вирази; якщо вкладений об'єкт чи масив необмежено росте, документ роздувається; зовнішні інструменти (CSV-експорт, BI), що очікують плоскі колонки, потребують зворотного розгортання. Також оновлення однієї метрики все одно записується через повний шлях і не дає виграшу в продуктивності, а лише в зручності моделі.

### Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?

У CSV колаборації записано одним рядком із роздільником `;` (наприклад, `Rema;Selena Gomez`). Рядок не має структури: щоб знайти треки виконавця, довелося б шукати підрядок регулярним виразом, а це ненадійно (ім'я може бути частиною іншого імені, є різні пробіли навколо `;`) і не користується індексом. Масив `artists` робить кожне ім'я окремим елементом:

- точний збіг за виконавцем: `{ artists: "Drake" }` працює по елементу масиву;
- по масиву можна побудувати multikey-індекс, який індексує кожне ім'я окремо;
- `$in`, `$all` (усі з переліку), `$elemMatch` і `$size` дають умови на кількість виконавців чи колаборації: 30075 треків у `tracks` мають більше одного виконавця, і їх знаходить `{ "artists.1": { $exists: true } }`;
- `$unwind` + `$group` дає статистику по кожному виконавцю окремо, що і використано в Завданні 2: колаборація зараховується кожному з учасників.

Компроміс: імена лишаються денормалізованими рядками, окремої колекції виконавців немає, тому перейменування чи об'єднання дублікатів потребує масового оновлення.

## Частина 2 - запити та пояснення

Код запитів лежить у `queries/part2_queries.js` і запускається командою `mongosh "$MONGO_URI" --file queries/part2_queries.js`. Скрипт друкує лише результат Завдання 2; для Завдань 1, 3 і 4 результати отримано виконанням тих самих запитів в інтерактивному mongosh (або Atlas).

### Завдання 1. Треки для вечірки

Запит `find` з фільтром і проєкцією. Умови на `danceability` і `energy` задано через крапкову нотацію в `audio_features`. "Вище 0.7" означає строге `$gt`, тому 0.7 не проходить. Тривалість "від 3 до 5 хвилин" включає межі, тому `$gte: 180000` і `$lte: 300000` по `duration_ms`. Усі умови в одному об'єкті поєднуються через AND. Датасет містить той самий `track_id` під кількома жанрами, тому трек може траплятися більше ніж один раз (наприклад, `LOKERA` у жанрах `latino` і `latin`).

Результат: 7311 треків.

### Завдання 2. Виконавці, у яких усі треки популярні

Конвеєр `aggregate`:

1. `$unwind: "$artists"` розгортає масив: трек із двома виконавцями дає два документи, тож колаборація зараховується кожному.
2. Перший `$group` за парою `(artist, track_id)` прибирає дублікати: той самий трек може бути в датасеті під кількома жанрами, і без дедуплікації він рахувався б кілька разів і спотворював би `track_count` та середнє. `$max` бере одне значення популярності для пари.
3. Другий `$group` за виконавцем рахує `$sum: 1` (кількість унікальних треків), `$min` і `$avg` популярності.
4. `$match` застосовується до неокруглених значень: `track_count >= 3` і `min_popularity >= 60` (шкала 0-100, тому 60% дорівнює 60).
5. `$sort` за середньою популярністю за спаданням, потім за кількістю треків і за ім'ям для детермінованого порядку; `$limit: 20`.
6. `$project` перейменовує `_id` на `artist` і округлює значення через `$round` до 1 знака в самому кінці, щоб округлення не впливало на фільтрацію. Усі чотири вихідні поля записано виразами (`track_count: "$track_count"`), тож порядок полів у виводі збігається з переліком у завданні (ім'я, кількість, мінімальна, середня популярність).

Результат: 20 виконавців, перший - Harry Styles (track_count 3, min_popularity 89, avg_popularity 92).

### Завдання 3. Нетипові треки

Конвеєр `aggregate`:

1. `$group` за `track_genre` рахує `$avg` та `$stdDevPop`. Використано генеральне (population) стандартне відхилення, бо в жанрі є всі його треки з датасету, а не вибірка.
2. `$addFields` обчислює поріг `avg + 2 * stdDev`.
3. `$lookup` повертається в `tracks`. Збіг жанру задано через `localField: "_id"` / `foreignField: "track_genre"`, а поріг передано змінною `let: { threshold }` у підконвеєр, де `$expr` з `$gt` порівнює `audio_features.tempo` із порогом. Порівняння строге (`>`) з неокругленим порогом. Рівність за жанром через `localField`/`foreignField` дешевша, ніж перевіряти й жанр у `$expr` для кожного документа. Підконвеєр сортує викиди за темпом за спаданням і проєктує `track_name`, `popularity`, `artists`, `audio_features.tempo` (`_id` лишається за замовчуванням).
4. Кінцевий `$project` округлює `avg_tempo` і `outlier_threshold` до 1 знака (лише для відображення), перейменовує `_id` на `genre` і виводить усі чотири поля виразами, щоб зберегти порядок із прикладу. `$sort` за жанром.

Результат: 114 жанрів (у `drum-and-bass` і `happy` нетипових треків немає, `outlier_tracks: []`), разом 3506 нетипових треків. Для `acoustic`: avg_tempo 119, outlier_threshold 178.5.

### Завдання 4. Треки для фонової роботи

Запит `find` з фільтром і проєкцією. Чотири умови поєднуються через AND, усі порівняння строгі, як у завданні: `loudness < -10` (`$lt`), `speechiness < 0.1` (`$lt`), `instrumentalness > 0.5` (`$gt`). `loudness` вимірюється в децибелах і майже завжди від'ємний, тому `< -10` відсікає гучні треки. `explicit: false` працює як булева умова, бо завантажувач привів `explicit` до bool.

Результат: 9324 треки.
